  <action>
    Perform a systematic accessibility audit and apply fixes across the entire component tree. Work through these categories in order:

    **1. Skip Navigation Link (if not already present):**
    - In `src/app/layout.tsx`, ensure a skip navigation link exists as the very first element inside `<body>`:
      ```tsx
      <a href="#main-content" className="sr-only focus:not-sr-only focus:absolute focus:z-50 focus:top-4 focus:left-4 focus:bg-gold focus:text-black focus:px-4 focus:py-2 focus:rounded-sm focus:font-semibold">
        Skip to main content
      </a>
      ```
    - Ensure the `<main>` element has `id="main-content"` and `tabIndex={-1}` (allows programmatic focus).
    - If skip nav already exists from Phase 2, verify it works correctly and has proper styling.

    **2. Landmark Structure:**
    - `<nav>` in navigation.tsx should have `aria-label="Main navigation"`
    - `<main>` in layout.tsx should have `role="main"` (implicit from `<main>` element, but verify it exists)
    - `<footer>` should have `aria-label="Site footer"` or a heading
    - Each `<section>` rendered by the Section component should ideally have an `aria-labelledby` pointing to its heading, or an `aria-label`. Since sections are generic wrappers, add an optional `ariaLabel` prop to the Section component if not already present.

    **3. Navigation Accessibility:**
    - Navigation links must indicate the current page with `aria-current="page"`. Check navigation.tsx -- if it uses `usePathname()` to highlight the current link, ensure it also sets `aria-current="page"` on that link.
    - Mobile menu button must have:
      - `aria-expanded={isOpen}`
      - `aria-controls="mobile-menu"` (matching the menu panel's `id`)
      - `aria-label="Open menu"` / `aria-label="Close menu"` based on state
    - Mobile menu panel must have `id="mobile-menu"` and `role="dialog"` or be within the `<nav>`.
    - When mobile menu opens, focus should move to the first menu link or the close button. When it closes, focus should return to the hamburger button.

    **4. Image and SVG Accessibility:**
    - All `<Image>` components must have descriptive `alt` text (not empty strings unless truly decorative)
    - Decorative images/SVGs (architectural motifs, line drawings) should have `aria-hidden="true"` and `alt=""`
    - The Ikigai Model diagram SVG (`model-diagram.tsx`) must have a comprehensive `aria-label` describing what the diagram shows (e.g., "Ikigai Architecture Model showing the four-phase flow: Blueprint, Build, Strengthen, Sustain, integrated across seven organizational pillars"). Also add `role="img"` to the SVG element.
    - Pillar icons in the grid should have `aria-hidden="true"` since the text labels provide the meaning.

    **5. Interactive Element Accessibility:**
    - All Button components: verify `focus-visible` outline styles exist (should be from Phase 1). Ensure buttons have accessible names (from text content or aria-label).
    - All Card components: if cards are clickable (links), ensure the entire card surface is the click target with a proper `<a>` tag, not a click handler on a `<div>`. If cards have "Learn More" links, ensure the link text is descriptive (e.g., `aria-label="Learn more about Strategic Architecture"`).
    - Check all links for descriptive text -- no bare "Click here" or "Learn more" without context.

    **6. Color Contrast Verification:**
    - Gold (#D4A843) on hunter green (#355E3B): Calculate contrast ratio. Gold on hunter green is approximately 3.2:1 -- this passes for large text (3:1) but NOT for body text (4.5:1). If gold text is used as body-sized text on hunter green, it must be changed to a lighter gold or white.
    - Gold (#D4A843) on black (#111111): approximately 6.5:1 -- passes AA for all text sizes.
    - White on hunter green (#355E3B): approximately 7.5:1 -- passes.
    - Audit all instances where gold text appears. It should ONLY appear as:
      - Large text (18px+ or 14px+ bold) on dark backgrounds
      - Decorative elements (borders, accents, backgrounds) -- not as readable text on light backgrounds
    - If any gold body text exists on hunter green, change it to white or use gold-100/gold-200 (lighter) instead.

    **7. Heading Hierarchy:**
    - Verify each page has exactly one `<h1>`
    - Verify headings follow logical order (h1 > h2 > h3, no skipping levels)
    - Check that SectionHeading component properly outputs the correct heading level via its `headingAs` prop

    Do NOT change the visual design. All fixes should be invisible to sighted users (ARIA attributes, semantic HTML improvements, focus management). The only visual addition should be the skip navigation link when focused.
  </action>

    - Skip navigation link appears when focused (Tab from page load) and jumps to main content
    - Mobile menu button announces its state (expanded/collapsed) to screen readers
    - Ikigai Model diagram SVG has a descriptive aria-label
    - No heading hierarchy violations (check with browser dev tools accessibility inspector)
    - `aria-current="page"` appears on the active navigation link

  <name>Task 2: Audit and fix contact form accessibility and install axe-core for automated checking</name>

  <action>
    **1. Contact Form Accessibility:**

    Audit `src/components/sections/contact-form.tsx` and fix:

    - Every `<input>` and `<textarea>` must have an associated `<label>` element (using `htmlFor` matching the input's `id`). Do NOT use placeholder text as the only label.
    - Required fields must have `aria-required="true"` (or the HTML `required` attribute, which is equivalent).
    - If the form shows validation errors, each error message must:
      - Be associated with its input via `aria-describedby`
      - Use `aria-live="polite"` on the error container so screen readers announce errors when they appear
      - Be visually clear (not just color-coded -- add an icon or text prefix like "Error:")
    - The form submission success message must use `aria-live="polite"` so screen readers announce it.
    - The form's submit button must have clear text ("Begin the Conversation" or similar strategic CTA language, not "Submit").
    - If the form has a honeypot field for spam protection, it must be:
      - Hidden with `aria-hidden="true"` and `tabindex="-1"` so screen readers and keyboard users skip it
      - Hidden via CSS (`position: absolute; left: -9999px`) rather than `display: none` (some bots detect display:none)

    **2. Calendar Booking Accessibility:**

    Audit `src/components/sections/calendar-booking.tsx`:
    - The Calendly embed iframe must have a descriptive `title` attribute (e.g., `title="Schedule a strategy call with Ikigai Consulting Group"`)
    - If there is a loading state before Calendly loads, add `aria-busy="true"` and an `aria-label` describing what is loading

    **3. Install axe-core dev dependency for automated accessibility checking:**

    ```bash
    npm install -D @axe-core/cli
    ```

    After installation, run an axe scan against the built site to catch any remaining issues:

    ```bash
    npx serve out -l 3333 &
    npx axe http://localhost:3333 http://localhost:3333/about http://localhost:3333/services http://localhost:3333/model http://localhost:3333/impact http://localhost:3333/contact --exit
    ```

    Fix any violations axe reports. Common violations to expect:
    - Missing form labels (should be fixed above)
    - Color contrast issues (should be fixed in Task 1)
    - Missing alt text (should be fixed in Task 1)
    - Missing landmark roles (should be fixed in Task 1)

    Note: axe-core won't catch everything (it catches ~30-40% of a11y issues). The manual audit in Task 1 covers what automation misses.
  </action>
